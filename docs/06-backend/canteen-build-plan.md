# Canteen build plan (ADR-016)

Status: proposed 2026-10-25. Design only. Slices are in dependency order; each is shippable and leaves the invoice path working. Estimates are working days for one developer including tests, audit events and the help-page update for that slice; the range is best case to realistic.

**Total: 48 to 61 days (midpoint about 54).** The earlier 42 to 59 estimate is raised at the low end for two reasons found in the code: about 18 backend and 9 frontend files assume every sale has an invoice (slice 2.2b), and the menu admin builder is a real screen set, not a form (slice 1.2). Phase 1 depends on no unanswered client item.

Every migration below is run by the owner role. For each new table, state in the migration comment whether it is append-only or lifecycle, then update `database/scripts/harden_append_only_privileges.sql`, the read-back in `app/Console/Commands/HardenDatabase.php`, and `tests/Database/AppendOnlyPrivilegesTest.php` in the same slice. No new table needs DELETE, so the DELETE allow-list is unchanged.

**1.2 Meal configuration model and admin builder: 6 to 8 days.**
- **Built 2026-10-25** (not committed at the time of writing). Migrations `2026_10_25_113805_create_dish_categories_and_dishes_tables`, `..._113806_add_menu_hidden_to_products_table`, `..._113808_create_meals_and_option_tables`, `..._113809_create_menu_prices_table`; 32 `Menu` operations (`docs/05-api/operation-inventory.md`, "Meal menu"); `app/Services/Menu/*`, `MenuController`, `MenuPriceController`; admin screens `/admin/menu/dishes`, `/admin/menu/meals`, `/admin/menu/prices/:mealId` (nav section "Meal menu"); `MealMenuSeeder` run on demand with `php artisan db:seed --class=MealMenuSeeder` (not in `DemoDataSeeder`, refuses production). Decisions: (1) every menu operation, reads included, is `CATALOG_MANAGE` (the till's own payload is slice 1.3). (2) A meal is created together with its pricing group, so "exactly one `prices_the_meal` group" holds from birth; the flag can only be moved (PATCH `prices_the_meal: true` on another active CHOICE group that is 1 to 1), never cleared, and that group cannot be hidden. (3) "Categories that appear in a meal" means the categories of the dishes offered (active or hidden) in its pricing group; a dish in a Side group never makes its category priceable. (4) A price edit appends a row effective now or later; a past `effective_from` is refused (a back-dated row would silently re-price history); the instant has one-second precision, so two edits of one key within the same second are refused; saving the price already in force records nothing. (5) The hidden backing product (meal and add-on) is `menu_hidden = true`, `active = false`, `selling_price 0.00`, `track_inventory = false`, tax class `NON_VAT` (open item 7), SKU `MEAL-<NAME>` / `ADDON-<LABEL>`; it is excluded from the product list, barcode lookup, CSV export and `ProductService`. It is inactive on purpose: until slice 1.3 resolves meals, a client that names it is refused as `PRODUCT_INACTIVE` instead of selling it at 0.00; slice 1.3's resolver must accept it for a meal line without reactivating it. (6) Dish category `code` is generated from the first name and immutable. (7) Audit: `MENU_DISH_CREATED|RENAMED|UPDATED|HIDDEN|SHOWN`, `MENU_PRICE_CHANGED`, `MENU_STRUCTURE_CHANGED` (categories, meals, groups, options; `after_metadata.change` says created/updated/hidden/shown/reordered). Known limits: the product CSV import still matches by SKU over all products, so a CSV row that reuses a backing SKU would hit the unique index and fail that row; the seeder matches by name, so a seeded dish that was renamed is created again if the seeder is re-run.
- Scope: `dish_categories`, `dishes`, `meals` (+ hidden backing product), `meal_option_groups`, `meal_options`, `menu_prices`; services enforcing the configuration rules (one `prices_the_meal` group per meal, min <= max, price rows only for categories that appear); admin screens for dishes (rename/hide/reorder), meals and groups, a price grid per meal by dish category with history view; seed Standard Meal (60/68, vegetable 60), Combo Meal (80/85, flagged "pending client confirmation"), rice add-ons 15 and 10.
- Areas: new `app/Services/Menu/*`, `MenuController`, `MenuPriceController`, admin pages under `resources/js/pages/admin/menu/`, `CATALOG_MANAGE` gates, audit event types.
- Migration: seven tables. `menu_prices` append-only (REVOKE UPDATE); the rest lifecycle, no DELETE.
- Tests: invariants MENU-003/004/005, price effective at an instant (before/after `effective_from`), rename leaves history, cashier forbidden, audit written.

**1.3 Checkout: meal resolution, snapshot, new picker, rice pop-up: 6 to 8 days.**
- **Built 2026-10-25** (not committed at the time of writing). Migrations `2026_10_25_130000_add_meal_snapshot_columns_to_sale_items_table` and `2026_10_25_130001_create_sale_item_selections_table`; API `menuGet` (`GET /menu`, any signed-in user, no capability) and `items[].meal` on `saleFinalize` (`docs/05-api/operation-inventory.md`, "Till menu"); `app/Services/Checkout/MealLineResolver.php` (+ `ResolvedMeal`, `ResolvedMealLine`), `app/Services/Menu/TillMenuBuilder.php`, `MenuGroupPath`; new errors `MEAL_NOT_AVAILABLE` (409) and `MEAL_SELECTION_INVALID` (422); SPA `pos/mealMenu.js`, `pos/MealPicker.jsx` (the old `mealMenus.js`, screen-only `MealPicker` and the SKU lookup are deleted). Decisions: (1) **Request shape** is the ADR's `items[].meal = {meal_id, choices: [{group_id, option_id}], addons: [option_id]}`; an item is a `product_id` or a `meal`, never both; no money field exists under `meal` and the request validator drops unknown keys, so a client price cannot reach the checkout. (2) **Quantity is 1 per meal item** (MENU-003); the till sends a cart quantity of N as N items, so the cart still steps its quantity (a whole number from 1 to 99 for a meal line). (3) **One meal item becomes the meal line plus one line per add-on**, add-on lines carry `meal_id`, `meal_name_snapshot`, the same menu path and `parent_line_number`; the meal's `line_discount_amount` and `order_discount_eligible` apply to the meal line (the add-on inherits eligibility, never a line discount) and the till hides the per-line discount box on a meal line (the order-level discount still applies). (4) **Description** on the sale line, the invoice and refund/void printouts is computed at the sale from the snapshot: `product_name_snapshot` = "Standard Meal - Beef nilaga" ("Combo Meal - Beef nilaga + Pinakbet" with a side), add-on line = its label; `meal_name_snapshot` keeps the bare meal name. The invoice snapshot schema (version 2) is unchanged: no new key, and a sale without a meal renders byte-for-byte as before. (5) `sale_item_selections` holds one row per chosen dish on the meal line (group, dish, dish category, `price_snapshot` on the pricing group's row) and one row on an add-on line (group, label, add-on price). (6) `sale_items.menu_group_path_snapshot` is also filled for a plain product that sits in a menu group, as the ADR says (billing grouping); it is null otherwise. (7) **Backing products**: still inactive and `menu_hidden`; the resolver uses them without reactivating anything; a plain `product_id` naming one is `PRODUCT_INACTIVE`, and checkout also refuses any `menu_hidden` product on that path even if one were reactivated. (8) **Tax class of a backing product** now follows the store's tax registration on the day it is created (VATABLE for a VAT store, NON_VAT otherwise): the fixed NON_VAT of slice 1.2 made every meal fail with a 500 `InvalidTaxConfigurationException` in a VAT-registered store (TAX-NV-002/003). Existing backing products keep their class; a store that changes registration re-classifies them like any product (open item 7 still stands). (9) The till menu lists only what the checkout accepts (visible group chain, active group/option/dish/category, a price in force; a pricing-group choice or add-on with no price is left out; a meal that cannot be completed is left out), so the picker cannot build a selection the server would refuse for being hidden; it is read when the register opens (not yet re-read at shift open or on a refusal). (10) Known limits: every meal line moves the one backing product's stock balance row, so two tills ringing meals serialize on that row for the length of the sale transaction (same as any very popular untracked product; stock movements are written for untracked products today); product reports label a meal row with the backing product's current name, so renaming a meal re-labels it in the product reports (dish renames never reach any report).
- Scope: `GET /menu` payload for the till; `items[].meal` accepted by finalize (OpenAPI + request validation); server resolves selections and price, creates the meal line plus add-on lines, writes `sale_item_selections` and the new `sale_items` columns; replace `mealMenus.js`, `MealPicker.jsx` and the SKU lookup in `CatalogPanel.jsx` with the menu-driven picker (step 1 dish category, step 2 dish, then the rice pop-up, skippable); idempotency hash includes the `meal` structure; invoice snapshot (invoice mode) prints meal and dish in the line description; sales detail shows the selection.
- Areas: `CheckoutService` (a `MealLineResolver` collaborator, so the transaction script stays readable), `SaleItem` model, `SaleDetailResource`, `Pos.jsx`, `CartPanel.jsx`, the invoice snapshot renderer.
- Migration: `sale_items` + nullable `menu_group_path_snapshot`, `meal_id`, `meal_name_snapshot`, `parent_line_number`; new `sale_item_selections` (append-only). Update the hardening script for the new table.
- Tests: client price ignored (tampered price); min/max violations; inactive option; rename a dish after the sale and the sale/report/reprint is unchanged (MENU-001); repricing mid-day; add-on line refunded alone; end-to-end invoice with a meal; the existing 5ec4c51 picker tests are replaced.

## Phase 3 — Employees and credit: 13 to 17 days

Depends on 2.1 (payment CHECK constraints) and 2.2 (slip carries the employee). Needs the client's answer on the cut-off end date (assumed end of month) and the limit for SUB (assumed the same 1,500) before UAT, not before building.

**3.1 Employees and lookup: 4 to 5 days.** `employees`, `employee_code_sequences`, `billing_parties` (seeded TSC and Subcontractors), `credit_policies`; admin screens with `EMPLOYEE_MANAGE`, CSV import with generated codes, deactivate, printable QR/ID card sheet; till lookup by scanner text or typed number (name, type, active only). Migration: those four tables plus a column-level UPDATE grant for `employees` that excludes `employee_code` and `employee_type`. Tests: code format and gap-free under concurrent creation, never reused, cashier cannot create (403), lookup scoped to store, inactive refused.

**3.2 Credit tender, ledger, limit, concurrency, reversals: 7 to 9 days (includes the start-of-sale "Who is paying?" choice, +1 day).** `CREDIT` tender (sole payment, no payment step in `TenderPanel`), `sales.employee_id`, `employee_credit_entries` ledger, `CutOff` value object (store timezone, end of month), `LockableResource::Employee` inserted at order 2 and the order documented in architecture.md, over-limit refusal `CREDIT_LIMIT_EXCEEDED`, credit-status preview endpoint and the cashier warning, refund/void settlement to `CREDIT` writing REVERSAL in the original period, readings show credit as a separate non-cash line. Migration: `payments`/`refund_settlements` CHECK add `CREDIT` (if not done in 2.1), `sales.employee_id`, `employee_credit_entries` (append-only). Tests (tests/Database where concurrency matters): two connections charging the same employee near the limit, exactly one succeeds; cut-off boundaries (15th/16th, 28/29/30/31, midnight Manila); expected cash and change unchanged by a credit sale (CREDIT-002; confirm the open cash-change bug in the project memory is fixed or independent before relying on drawer assertions); refund of an earlier period; credit mixed with cash refused.

**Start-of-sale "Who is paying?" choice (client request, recorded 2026-10-25; part of 3.2).** The client's process sheet asks for the Cash or Credit choice BEFORE any item is ordered. Design: a new sale starts on a first screen with two large buttons, **Cash** and **Credit**. Cash opens the register at once (a single tap; the open question below is whether the register should instead open by default with a Credit switch at the top, so a cash sale costs no extra tap in the lunch queue). Credit asks for the employee (QR scan or typed ID), shows the name and the remaining limit for the current cut-off, then opens the register with the employee attached to the sale, so the limit warning and the supervisor-code override appear while items are rung, not only at the end. A credit sale skips the Payment step and goes to the slip. The cashier can switch between cash and credit while the cart is open without losing items. A "new employee" path at the till is NOT offered to cashiers (ADR-016: employees are created by EMPLOYEE_MANAGE); if the client wants it there, it needs a supervisor code first. Needs 3.1 (employees) and 3.2 (credit); until then the Payment step is the only place payment types appear. Open item 13: Cash-first screen versus register-open-with-a-Credit-switch, to be confirmed with the client.

**3.3 Supervisor override: 3 to 4 days.** `user_override_codes`, `credit_override_grants`, `CREDIT_LIMIT_OVERRIDE` capability, endpoints to set/reset a code, list approvers and grant, the till modal (named approver plus code), checkout consumption under the employee lock, lockout and throttle, all audit events and their filters in `recordsParts.jsx`. Migration: two tables; grants limited to counter columns and `consumed_at`. Tests: wrong code x5 locks even when the surrounding checkout rolls back; token single-use (parallel replay), wrong terminal/employee/amount, expired, approver equals cashier refused, code equals password refused, every path audited, no code or token in logs or audit payloads.

## Phase 4 — Billing: 7 to 8 days

**4.1 Billing generator and report: 4 to 5 days.** Service producing party -> account (employee) -> meal type -> item/dish from the ledger and snapshots for a range or named cut-off, as-of date, adjustments flagged, on-screen plus print and CSV export; optional saved `billing_runs` with `BR-` numbers; separate runs for TSC and SUB. Migration: `billing_runs` (append-only). Tests: totals equal ledger net; re-run after a later refund shows the adjustment and the saved run is unchanged; a renamed dish does not change an old statement; party separation.

**4.2 Cheques against what is owed: 3 days.** `billing_cheques`, `billing_cheque_allocations`, `BILLING_MANAGE`, owed-by-period view, return a cheque (status RECEIVED to RETURNED, reinstating the owed amount), idempotent recording (two operation types added to `IdempotencyOperationType`). Tests: over-allocation refused under concurrency, cheque never creates a cash movement, returned cheque restores balance.
