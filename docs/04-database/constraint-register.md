# Constraint Register — TindaFlow POS

## Status

DRAFT — Stage 5, awaiting owner review. Companion to
[database-schema.md](database-schema.md). Lists every significant
invariant from [invariants.md](../02-domain/invariants.md) (and a small
number of structural rules invariants.md doesn't separately number),
its frozen source, its enforcement level, and its mechanism — making
explicit which invariants PostgreSQL itself protects today versus which
Stage 6 must still enforce transactionally or as application policy.

**Enforcement levels:**
- **DATABASE** — PostgreSQL rejects the violating write itself; no
  application code path can bypass it, including a bug.
- **TRANSACTION** — requires a specific transactional pattern (row lock,
  aggregate recheck, single-transaction atomicity) that Stage 6's
  service layer must implement; the database provides the primitives
  (`SELECT ... FOR UPDATE`, foreign keys, unique constraints) but cannot
  express the full rule declaratively.
- **APPLICATION POLICY** — depends on business logic or authorization
  state the database has no way to represent (e.g., capability
  evaluation), and is not expected to ever become a database constraint.
- **COMBINED** — a DATABASE constraint provides a partial guarantee;
  TRANSACTION or APPLICATION logic closes the remaining gap.

All 13 partial unique indexes, 59 CHECK constraints (corrected
2026-09-16 from an earlier miscount of 57 — recounted directly via
`pg_constraint` while verifying this pass; no CHECK constraint was
added or removed by either hardening pass, the original count was
simply wrong), and the FK delete-action policy referenced below were
confirmed live against a running PostgreSQL 17 instance — see
[schema-validation.md](schema-validation.md) Pass A.
