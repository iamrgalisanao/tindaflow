# ADR-018: Cloud Activation, Hardware Binding and Bounded Offline Operation

## Status
Accepted — 2026-11-24, on the owner's sign-off of the design document "TindaFlow Cloud Activation and Licensed Deployment — Design Document v2" (kept outside the repository; this ADR is the repository's record of its decisions). Not part of the frozen Stage 1–6C corpus. **Design only: no code accompanies this ADR. Amended 2026-11-24, after sign-off, on the owner's instruction: the offline tolerance (D6) is 30 days, not 7, and emergency extensions add 30 days.** Still open: counsel's review of the license agreement text and the proposed retention periods, the Phase 1 spike (below), and the owner's go/no-go confirmation of the sealed break-glass ADMIN (design decision O-1).

Amends, in place:
- **ADR-014** decision 6, "a license never stops selling", and its Consequences line "existing tills keep working under any license state": a license now never stops a shift that is within its limits (an open shift keeps selling until it closes; once the license is EXPIRED or LOCKED, a shift older than 18 hours is stopped). The till-cap license file is replaced, after migration, by the activation certificate below.
- **ADR-015**: enrollment now also depends on activation. `TerminalSeats::maximum()` returns the certificate's `seats` in ACTIVE or WARNING, 0 in NOT_ACTIVATED, EXPIRED or LOCKED, and `null` (no cap) in LEGACY. An already-enrolled till is never blocked (ADR-014 decision 5 stands).
- **ADR-002**: its list of operations that work without internet stays true (the license check is local), and offline checkout is unchanged. Its sentence that only optional, non-authoritative conveniences may need internet is amended: one successful renewal per certificate life is now required. (No browser-side offline sale queue exists, so no replay rule is needed; see `offline-strategy.md`.)
- **ADR-013** decision 5: the software clock check it deferred ("not built now") is now built, because licensing needs trusted time. The RTC-battery install check stays. A Windows host with Docker Desktop is allowed at 8 GB or more (decision 2), and the UPS requirement of decision 1 applies.
- **ADR-008**: every backup restore now ends with a provider Re-chain (runbook RB-7), because a restore can roll the certificate chain back (decision 5).

## Context
ADR-014's license caps tills only. It is bound to the `DeploymentId`, the last 8 hex characters of the oldest store's UUID. A copy of the database carries that UUID, so a clone still verifies, and an expired license never blocks a sale. `docker/compose.yaml` also builds from source, so a client holding the source can rebuild with their own public key. Nothing stops a copied installation from trading.

The first client is the TSC canteen: one old desktop (Intel i5-6500, 8 GB RAM, Windows 10 Pro 22H2 with commercial Extended Security Updates, Docker Desktop on WSL2) acting as server and till, in SLIP mode (ADR-016), with internet that may be down for days. The mechanism must work without permanent internet, must not put a vendor account inside client data (ADR-014 rejected that), and must fit one store per server.

Decisions the owner had already taken: a cloud control plane with a local till, one-time activation data and no ongoing data sync (D1); sales continue while the internet is down (D2); the local manager owns users, catalog and prices after go-live (D3); more clients without client code changes (D4); enforcement strength Medium, deter and detect (D5); offline tolerance 30 days from the last renewal (D6, amended from 7 days by the owner on 2026-11-24, after sign-off); hardware binding on (D7); the provider runs a small control plane (D8); a manager account exists after activation (D9).

## Decision

### 1. An activation certificate, renewed from a provider control plane
The installation is activated once, then runs fully offline between renewals. The control plane signs a short-lived **activation certificate** (Ed25519 over a JCS-canonical JSON payload, RFC 8785) that binds `deployment`, `store`, `installation` (a random UUID made at activation), the hardware fingerprint, `seats`, `mode` (`enforce` or `report`), `iat`/`exp`, and a chain position (`seq`, `prev`, `jti`). A `kid` selects the verifying key from a list of vendor public keys held as code constants in `config/tindaflow.php`, never read from the environment. Certificates use one key family; extension and `time_reset` codes (decision 6) use a second, and a code's type is part of its signed payload, so each key serves one purpose.

`exp` is the renewal time plus 30 days, rounded **up** to the next 05:00 in the store's time zone, so a certificate lives **30 to under 31 days** and expiry never falls in trading hours. Renewal returns the current certificate unchanged if it is under 24 hours old, so `seq` advances at most once a day. The scheduler tries to renew at start-up and hourly (±10 min jitter). Key rotation: a new `kid` ships one release ahead and signing switches after all clients run it; on compromise an image ships with the old `kid` in `revoked_kids`, which offline clients receive only with their next image.

### 2. The license gates shift open; an expired or locked license also caps an open shift
States, evaluated locally with no network: **ACTIVE** (until 7 days before `exp`), **WARNING** (the last 7 days), **EXPIRED** (past `exp`), **LOCKED** (clock rollback, fingerprint mismatch, revocation or a broken chain), plus **NOT_ACTIVATED** and **LEGACY** (decision 11). LOCKED takes precedence.

- `shiftOpen` is refused unless the state is ACTIVE or WARNING. Refusal applies only when enforcing: LEGACY, and certificates with `mode=report`, log the decision and refuse nothing.
- A shift already open keeps selling until it closes. Only when the state is EXPIRED or LOCKED, a sale is refused once `trusted_now − opened_at` exceeds **18 hours** (`SHIFT_TOO_LONG`). In ACTIVE and WARNING there is no cap.
- Close, X/Z reports, reprints, voids, refunds and exports are never gated.
- The refusal is HTTP 409 with a new error code `LICENSE_NOT_ACTIVE` and `details.reason` in `NOT_ACTIVATED, EXPIRED, CLOCK_ROLLBACK, FINGERPRINT_MISMATCH, REVOKED, CHAIN_INVALID, SHIFT_TOO_LONG`. It is appended to `error-catalog.md` the way ADR-014 appended `TERMINAL_LIMIT_REACHED`.
- New middleware `EnsureLicenseActive` attaches in `routes/web.php` only. `app/Services/Checkout` and `SaleController` stay untouched (Stage 6C). A replay of a completed `shiftOpen` Idempotency-Key returns its original result even after expiry.

The longest unrenewed trading period is therefore **under 31 days 18 hours** (certificate life plus one 18-hour open shift). Each offline extension (decision 6) adds 30 days.

### 3. Trusted time
A high-water mark, `trusted_time_hwm`, lives in a new `license_state` table and only moves forward. It advances from each certificate's `iat`, each shift open and close, and a one-minute scheduler heartbeat that adds the larger of the wall-clock delta and the monotonic delta (boot id plus uptime), so a clock rolled back while the stack runs cannot stall it. Nothing is written inside the checkout transaction. `trusted_now = max(wall clock, trusted_time_hwm)`; the 18-hour cap uses it. A clock more than 1 hour behind the mark is LOCKED (`CLOCK_ROLLBACK`). An online renewal re-baselines the mark to control-plane time and audits it; offline, a provider-signed `time_reset` code does the same. Residual: time while the stack is not running is not counted, so validity is effectively measured in powered-on time against a clock a host administrator controls.

### 4. Hardware fingerprint
A small PowerShell host helper (a scheduled task as SYSTEM, at boot and hourly) reads `Win32_ComputerSystemProduct.UUID`, `Win32_BaseBoard.SerialNumber` and `Win32_BIOS.SerialNumber`, normalises them, rejects placeholder values, and writes `C:\ProgramData\TindaFlow\host\hardware.json` atomically. Each value is hashed as `SHA-256("tindaflow-fp-v1:" component ":" value)`: a vendor-wide prefix, so one PC under two deployments is detectable. The hashes are pseudonymous, not anonymous. Compose mounts the directory (not the file) read-only into both `app` and `scheduler`. **2 of 3** components must match; one change is reported at the next renewal and audited; 0 or 1 matches is LOCKED (`FINGERPRINT_MISMATCH`). A missing or older-than-26-hour file changes no state, but renewal is refused (`HOST_HELPER_STALE`). The helper also records the host's own `generated_at` as a second clock. The file is unsigned and can be copied with the stack (see the guarantees below).

### 5. Renewal chain and fork detection
Each renewal consumes the current certificate and returns its successor, like a rotating refresh token (except within 24 hours of issue, decision 1). A retry returns the stored successor only for the same client-generated, signed `request_id` (saved to disk before sending) and installation key. Any presentation of a `seq` below the latest issued, or an equal `seq` with a different `jti`, is `409 FORKED`: no certificate, provider alerted. One renewal runs at a time on the client (a database lock shared by the timer and "Check license now") and per installation on the control plane. An unsigned FORKED or REVOKED response never changes client state; only a vendor-signed revocation does. A validly signed certificate above the control plane's latest `seq` (after a control-plane restore) is accepted and audited. **A restore of a backup older than the latest issued `seq` is FORKED**; the provider's owner-verified **Re-chain** action recovers it (runbook RB-7). Accepted for TSC; before a third client, add an owner-held re-sync code with a yearly cap and an audit counter.

### 6. Offline extension
When an outage will outlast the certificate, the provider issues a signed extension: a compact 23-byte binary payload (type, `kid`, deployment, a short digest of `installation`, `base_seq`, days, ordinal, `iat`) plus the 64-byte Ed25519 signature, in Crockford base32 with a check character, groups of 5: about 170 characters (169 with separators), sent by SMS, Viber or email and pasted. The client computes `new_exp` as the next 05:00 at or after `max(base exp, iat) + 30 days`. An extension is valid only against the current `base_seq`, once (the ordinal is recorded), and at most **2 in a row** without an online renewal (a per-client setting). It never clears LOCKED. A renewal discards an unapplied extension. A copy duplicates the local ordinal record, so each copy can apply the same code once; this is accepted. A separate provider-signed `time_reset` code (same format, own type) resets the time mark for a clock set into the future. A code short enough to dictate would need a secret on the client, which a copier could extract, so that was rejected.

### 7. Revocation and suspension
Revoke (license breach): the next renewal returns a vendor-signed revocation and the client goes LOCKED at once. Suspend (non-payment): the control plane stops renewing and the client reaches EXPIRED with the usual warning. An offline client learns of either only when it next connects; the maximum latency is the certificate life plus one open shift, and the license agreement says so.

### 8. The control plane
A separate Laravel service with its own database, **provider-managed and hosted locally in the Philippines** on the provider's own server. It holds a registry (client, deployment code, installation, fingerprint hashes, seats, term, status, latest `seq`, last seen), an admin UI (MFA, reachable through a VPN) and a machine API (`POST /v1/activations`, `POST /v1/renewals`; TLS 1.2+ with certificate validation; versioned JSON). Only the machine API faces the internet, and the signing service accepts calls from that API only. Machine auth is a single-use activation code (at least 100 bits, 24 hours, stored hashed, rate-limited, idempotent for the same code and public key), then a client-generated Ed25519 key whose public half is registered; the control plane stores no shared secret. Requests are signed per RFC 9421 over `@method`, `@target-uri`, `content-digest` (RFC 9530) and `content-type`, with `keyid`, `tag`, an `expires` of 5 minutes or less measured from a server-issued nonce (so a client with a wrong clock can still renew) and a nonce cache on the server. The vendor signing key is generated inside a hardware security module such as a YubiHSM 2 (never exportable in the clear; backed up only as an M-of-N wrapped key held by different people), or, where none is bought, held encrypted and unlocked by a hardware token. The bundle lists a primary and at least one standby URL, which the client tries in order. Alerts: chain fork, fingerprint change, one fingerprint under two deployments, renewal from a new IP country, repeated clock anomalies.

### 9. Activation, and what crosses to the cloud
The control plane mints the store UUID when the client is registered and checks that the 8-hex deployment code and the store UUID are unique; the bundle carries `store_id`. `tindaflow:activate` verifies the certificate and fingerprint, then in one transaction creates the store with that id (`Store::$fillable` is `['name']`, so it uses `forceFill`, and clears the cached deployment id), creates the ADMIN and MANAGER through `UserService` with passwords typed on site, applies store settings, SLIP mode, slip footer and the default inventory location through the existing services, stores `license_state`, and creates `TILL-1` with its enrollment token (the till-creation logic is private to `CreateTerminal` and `TerminalController` today and is extracted into a shared service). It is idempotent per installation UUID and refuses a database that already holds sales unless `--force` is given (audited). `SaleDocumentSettingsService::changeMode` takes the freshly created ADMIN as actor and bypasses the ADR-014 unlock, which is enforced only at the route. `db:seed` (`AdminUserSeeder`, `Store::firstOrCreate`) must not run after activation: it would create a second store and change the `DeploymentId`. Events before a store exists go to the application log only, because `audit_events` requires a store. The offline path is `tindaflow:activate --request` (writes the installation UUID, public key and fingerprint hashes) then `--bundle` (the provider's reply bound to that key).

The license bundle carries store identity and business details, `sale_document_mode = SLIP`, the slip footer, the default inventory location, the `TILL-1` definition, seat count, the first certificate and the control plane URLs. Products, categories, prices and employees are imported on site. **Sales, shifts, stock, audit records, users, employees and credit limits never reach the cloud**; the provider sees license and device data only.

### 10. Roles and the Manager area
`USER_MANAGE` is added to MANAGER. Server-side rules check the target's current role and the requested role: in `UserService` (`create`, `update` including role and password, `setActive`) and in `OverrideCodeService::resetByAdmin`, reached by `POST /users/{userId}/override-code/reset`. A MANAGER may act only on CASHIER and MANAGER users; only an ADMIN may create, elevate to, or edit an ADMIN. Today `UserService` checks no actor role (`$actor` is for the audit row), so granting the capability without these rules would let a manager create or edit an ADMIN. A null actor (the console) is trusted, and each rule has a test. The last-active-ADMIN guard stays. A new `LICENSE_MANAGE` capability (MANAGER and ADMIN) covers license status, "check now" and extension entry. The client build includes a **Manager area**: Users, Catalog, Prices, Employees (credit limits read-only) and License status; without it, D3 cannot be met. Credit limits and the CSV import stay `EMPLOYEE_POLICY_MANAGE`, ADMIN only (the ADR-016 amendment of 2026-10-26). The back office stays at `/admin`; a MANAGER sees only the screens their capabilities allow, and every route stays gated by `can:`. The **break-glass ADMIN** is created at activation with a generated passphrase of 16 or more characters, written down and sealed on site; the provider never knows it, and every ADMIN sign-in is audited. This keeps ADR-014's rule of no vendor account in client data. Recovery uses the existing audited `tindaflow:reset-password` with the owner present; the technician sees the new password on screen, and the owner changes it at once. `USER_MANAGE` also lets a manager lift approver lockouts for credit and stock overrides; accepted, and the capability can be split later.

### 11. Distribution and migration
Prebuilt `tindaflow-web`, `tindaflow-app` and `tindaflow-backup` images from a private registry, pinned by digest. The client compose file has `image:` only, no `build:`; the backup scripts and certificates it mounts are shipped files. A new `scheduler` service (the app image running `php artisan schedule:work` as `www-data`, like the `migrate` service, with the `DB_OWNER_*` values blanked and the `app-storage` volume) runs the renewal. Image-only delivery deters casual changes but does not hide source, because a PHP image contains its code in plain text; it is not counted as a security control. Enforcement mode (`enforce` or `report`) is a **claim in the signed certificate, never an environment setting**, so a client cannot leave report-only on.

An installation holding an ADR-014 license keeps today's behaviour (state LEGACY, no enforcement) until `tindaflow:activate --adopt` reads its deployment code and seat count, renames the old file to `.migrated`, ignores the inline `TINDAFLOW_LICENSE` token and audits the change. With no vendor key in the build there is no enforcement, as in ADR-014. Commands: `license-keygen` stays (gains a `kid`); `license-issue` is vendor-only and retired after migration; `license-status` is extended (it already prints the deployment code, so no separate `installation-id` command is added); `create-terminal`, `load-canteen-menu` and `reset-password` stay; `load-sample-data` never runs on a client.

### 12. Host
Docker Desktop with automatic sign-in on a dedicated local account, all long-running services `restart: unless-stopped`, `.wslconfig` capping WSL2 at 5 GB, Windows Time on, power-on after AC loss, and the till browser in kiosk mode. Docker Engine inside WSL2 as a SYSTEM task was considered and not adopted (not a supported Docker Desktop setup). The host helper is installed as a signed script for TSC (a signing certificate is arranged in Phase 1), with an MSI before the third client.

### Amendment, 2026-11-24: the offline activation wire format (built in slice 4a)
Decision 9 left the bundle's shape open; this fixes it so the control plane and the client agree.
- **Request** (`tindaflow:activate --request`): JSON `{v: 1, typ: "tindaflow.activation-request", installation, installation_key, fingerprint}`. `installation` is a random v4 UUID and `installation_key` the base64 of an Ed25519 public key, both made on the PC and kept with the private half in `storage/app/license/installation.json` (written once, never replaced). `fingerprint` is null until the host helper exists.
- **Bundle** (`--bundle=FILE`): one vendor-signed token in the same wire form as a certificate (`base64url(JCS(payload)).base64url(signature)`, the same `kid` key ring, opened by one shared `SignedEnvelope`). Payload `v: 1`, `typ: "tindaflow.bundle"`, exactly the fields `certificate`, `control_plane` (1 to 4 `https` URLs, primary first), `default_location`, `deployment`, `iat`, `installation`, `installation_key`, `kid`, `sale_document_mode`, `slip_footer` (or null), `store_id`, `store_name`, `till_code`, `typ`, `v`. The bundle is bound to one PC by `installation` and `installation_key`; business details beyond the store name are entered on site, not carried.
- **Checks before anything is written:** the build has a vendor key; the bundle and its certificate verify; the bundle matches this PC's identity; the certificate's store, installation and deployment agree with the bundle, and the deployment is the last 8 hex digits of the store id (`DeploymentId::shorten`); `seats` is at least 1; the certificate has not expired; and the certificate's `iat` is no more than 1 hour ahead of this PC's clock (a clock further behind the provider's would lock the PC out with `CLOCK_ROLLBACK` at once). It refuses a database that already holds sales or a different store.
- **Effect:** one transaction creates the store with the provider's id, the break-glass ADMIN (a generated 20-character passphrase shown once, never stored), an optional MANAGER whose password is typed on site, SLIP mode and footer, the default stock location and the first till, and stores the certificate in `license_state` and moves the trusted-time mark to its `iat`. Re-running with the same bundle changes nothing.
- **Not built yet:** `--adopt` (the ADR-014 migration), `--force` (audited activation over existing sales), the online path, the fingerprint (needs the host helper), reading the seat count from the certificate in `TerminalSeats`, and the enrollment token for the first till (issued from the Terminals screen, as today).

### Amendment, 2026-11-24: the renewal wire format (built in slice 5a)
Decisions 1, 5 and 8 left the renewal conversation open; this fixes the client side so the control plane can be built against it. The bundle's `control_plane` URLs are kept in `license_state` (primary first).
- **Nonce:** `GET {url}/v1/nonce` returns `{"nonce": "<16 to 256 characters of A-Z a-z 0-9 . _ ~ : / + = ->"}`. The server measures the 5-minute window from when it issued the nonce, so the client sends no `created` or `expires` of its own clock.
- **Request:** `POST {url}/v1/renewals`, `Content-Type: application/json`, body `{v: 1, request_id, installation, certificate, fingerprint}` where `request_id` is a client-generated UUID, `certificate` the token held, and `fingerprint` null until the host helper exists. The request is signed per RFC 9421 (label `sig1`, Ed25519 with the installation key) over `@method`, `@target-uri`, `content-digest` (RFC 9530, SHA-256 of the exact body) and `content-type`, with `keyid` = the installation UUID, `tag` = `tindaflow-renewal` and `nonce`.
- **Answers:** `200 {v: 1, status: "RENEWED" | "UNCHANGED", certificate}`; `200 {v: 1, status: "REVOKED", revocation}`, where `revocation` is a vendor-signed token (`typ: "tindaflow.revocation"`, exactly `v, typ, kid, store, installation, iat`); `409 {error: "FORKED"}`. A transport failure, `429` or `5xx` moves on to the next URL; anything else is final. TLS certificates are always validated and redirects are never followed.
- **What the client accepts:** a returned certificate must verify, belong to the same installation, store and deployment, have a `seq` not below the one held (the same `seq` only with the same `jti`), and not be expired. A gap in the chain (not `seq + 1`, or `prev` not the SHA-256 of the held token) is accepted, since a provider re-chain or a control-plane restore legitimately produces one, but the audit event says `chain_gap`. `UNCHANGED` must carry the held certificate. An unsigned `REVOKED` or `FORKED` changes nothing; only a signed revocation sets `revoked`.
- **Time:** an accepted new certificate moves the trusted-time mark to its `iat`, even backwards (the online re-baseline of decision 3); the audit event records the old mark when it moved back by more than an hour.
- **Retries:** the `request_id` is saved before the request is sent and reused until an answer is applied, so a retry after a lost answer is the same request. One renewal runs at a time (a cache lock in the database). The scheduler runs `tindaflow:license-renew --jitter=600` hourly. A start-up attempt needs the `scheduler` service and is not built yet.
- **Not built yet:** setting `chain_invalid` (needs the append-only certificate history), reading `seats` from the certificate, extension and `time_reset` codes, and the control plane itself.

### Amendment, 2026-11-25: the host helper and its file (built in slice 6)
Decision 4 is built as `docker/host-helper/` (PowerShell, no dependencies). Details the ADR left open:
- **File:** `C:\ProgramData\TindaFlow\host\hardware.json`, `{"v": 1, "generated_at": "<offset ISO time, the host's own clock>", "fp": {"smbios_uuid", "board_serial", "bios_serial"}}`, each value the lower-case SHA-256 of `tindaflow-fp-v1:<component>:<normalised value>`. Normalising is: collapse white space, drop surrounding braces, upper-case. It is written atomically (a sibling file swapped in) as UTF-8 without a byte order mark. The container sees the folder read-only at `/var/tindaflow-host` (`TINDAFLOW_HOST_DIR` in compose).
- **Placeholders:** a component that is empty, shorter than 3 characters, one repeated character (all zeros, all F's), or a known manufacturer filler ("To be filled by O.E.M.", "Default string", "None", ...) is refused. If ANY of the three is refused the helper writes nothing and logs why, because a certificate binds all three and the strict certificate reader requires three hashes. **Commissioning check:** `Update-HardwareFile.ps1 -Check` says which components a PC can supply, without printing values and without writing. A development PC checked on 2026-11-25 reported a placeholder BIOS serial, so this is a real risk for the pilot PC: it must pass `-Check` before the Phase 7 rehearsal. If it does not, a decision is needed (a different binding for such a PC); the helper deliberately does not invent a value.
- **Install:** `Install-HostHelper.ps1` (elevated) copies the scripts to `C:\Program Files\TindaFlow\host-helper` (administrators write, nothing else), creates the data folder (SYSTEM and administrators write, everyone reads) and registers two SYSTEM tasks, at start-up and hourly, with `AllSigned` by default (the code-signing certificate is a Phase 1 item; `RemoteSigned` or `Bypass` for a rehearsal on an unsigned copy). A failure leaves the previous file to age and appends to `hardware-helper.log` beside it.
- **Application side:** the file is FRESH only when well formed and its `generated_at` is under 26 hours old. FRESH gives the license gate its observed fingerprint (2 of 3 must match the certificate, fewer is LOCKED `FINGERPRINT_MISMATCH`); missing, stale or invalid gives none, which changes no state. `tindaflow:activate --request` is refused without a fresh file, and a renewal is refused before anything is sent (`HOST_HELPER_STALE`), as the provider also would. The heartbeat uses the file's `generated_at` as a second clock: it can move the trusted-time mark forward and never back. `tindaflow:license-status` now evaluates the stored certificate (it previously always reported NOT_ACTIVATED once a key was present) and prints the file's state.
- **Still open:** the file is unsigned and can be copied (the ADR's residual risk); the helper's installer and tasks have been checked only by reading and by its self-test, not on the pilot PC.

### Amendment, 2026-11-25: the scheduler service (built in slice 7)
Decision 11's `scheduler` service is in `docker/compose.yaml`.
- **What it runs:** the app image as `www-data` (the entrypoint waits for the database first), with `DB_OWNER_*` blanked, the `app-storage` volume and the host folder read-only. The command tries one `tindaflow:license-renew` at start-up, then `exec php artisan schedule:work`; the `;` between them means a renewal that fails (no network, not activated) never stops the scheduler. It starts after `app` is healthy, which is after `migrate`. It sits on the `backend` network only; the provider is reached over the host's ordinary outbound route.
- **Liveness:** the schedule touches `storage/framework/scheduler-alive` every minute and the container's health check fails when the file is older than 3 minutes, so a dead or stuck scheduler shows in `docker compose ps` rather than letting the certificate run out unseen. This is the only signal; there is no alert yet.
- **Overlap locks** on the heartbeat and the renewal now expire after 5 and 25 minutes instead of Laravel's 24 hours. They live in the database cache, so a container killed mid-run (a restart, a power cut) would otherwise have blocked the license commands for a day.
- **Checked:** the compose file resolves under `docker compose config`, and its shape is pinned by tests. It has **not** been run as containers (no Docker engine was running on the build machine); that first run belongs to the Phase 1 spike on the pilot PC.

### Note, 2026-11-25: a received revocation has no way back
As built, once an installation has applied a signed revocation (`license_state.revoked`), it stops asking for renewals, no signed document clears the flag, and `tindaflow:activate` treats the installation as already activated. So decision 7's revocation is **permanent for that installation**. The provider's `license:revoke` says so and asks for the deployment code to be typed back; non-payment is what `license:suspend` is for, and it can be undone. A revocation can be taken back at the provider only while the PC has not received it. If reinstatement is wanted, it needs its own signed document (or a defined re-activation procedure) and a decision; the earlier client message that promised the provider could reinstate was wrong and is corrected.

### Amendment, 2026-11-25: offline extension and time-reset codes (built in slice 8)
Decisions 3 and 6, with the points they left open.
- **Payload, 23 bytes, big-endian:** type 1 (1 = extension, 2 = time reset), key id 1, deployment 4, installation digest 6 (first 6 bytes of SHA-256 of the installation UUID), `base_seq` 4, days 1 (1 to 30; 0 for a reset), ordinal 2, `iat` 4 (Unix seconds). The signature is Ed25519 over exactly these bytes.
- **Written form:** the 87 bytes as 140 Crockford base32 characters (the 4 spare bits zero) plus Crockford's check symbol (the value modulo 37, symbols `0-9 A-Z` less `I L O U`, then `* ~ $ = U`), in groups of five: 169 characters. Reading ignores case, spaces and hyphens and reads `I`, `L` as 1 and `O` as 0. The golden vectors hold three codes (as digests) and the independent Node check rebuilds them.
- **Code keys** are the second family: `tindaflow.license.code_keys`, numbered 1 to 255 because the payload has one byte for the number, with `revoked_code_keys`. Constants in code; a build with none accepts no code.
- **One ordinal counter** per installation covers both types and only grows, across certificates: a code is applied only if its ordinal is higher than every one applied before. Issuing a newer code therefore retires any unapplied older one.
- **Extension:** `new_exp` is the next 05:00 (store time zone) at or after `max(certificate exp, iat) + days`. "Base exp" is read as the **certificate's** expiry, not an earlier extension's, so two codes issued early do not stack. A code that would not make the license run longer, or whose period is already over, is refused and not used up. At most 2 in a row, fixed in the client; the provider also enforces a per-deployment limit of 0 to 2 (the ADR's per-client setting can lower it, not raise it). Refused while LOCKED or revoked. A new certificate discards the extension and restarts the count.
- **Time reset:** sets the trusted-time mark to the code's `iat`, even backwards, and audits the old mark. Allowed while locked by clock rollback (that is what it is for), never when revoked. Because the host helper's file may have been stamped under the wrong clock, the stamp in force at a reset (and at an online re-baseline) is set aside: the heartbeat does not use that one stamp to push the mark forward again.
- **Both:** the code's `base_seq`, deployment and installation must match the certificate held, and an `iat` more than 1 hour ahead of the PC's clock is refused (correct the clock first). Applying shares the renewal's lock.
- **Entry:** `tindaflow:license-code` (asks for the code, since the check symbol can be a shell character). `tindaflow:license-status` shows the certificate number, which the provider needs, and any extension. **Not built:** entry in the Manager area, with `LICENSE_MANAGE`.
- **Residual, as accepted in decision 6:** a copy of the installation holds its own record of used ordinals, so each copy can apply the same code once.

### Amendment, 2026-11-25: the Manager area (built in slice 9)
- **What it is:** decision 10's Manager area is the existing back office at `/admin`, filtered by capability. Users, Catalog and meal prices, and Employees (credit limits read-only without `EMPLOYEE_POLICY_MANAGE`) were already there once `USER_MANAGE` reached the manager; this slice adds **License** and the `LICENSE_MANAGE` capability (MANAGER and ADMIN). There is no separate client build.
- **License screen and API:** `GET /license`, `POST /license/renew` ("check now", 4 a minute per user) and `POST /license/codes` (10 a minute per user), session only, never gated by the license itself, returning no certificate, key or hardware hash. They call the same services as the console commands. Who asked is audited (`LICENSE_CHECK_REQUESTED`, and the actor on `LICENSE_EXTENDED`, `LICENSE_TIME_RESET` and `LICENSE_CODE_REFUSED`); the code itself never is. A refused code is `422 LICENSE_CODE_REFUSED`.
- **The warning:** the dashboard shows a notice to a `LICENSE_MANAGE` holder in WARNING, and in the states that refuse a new shift, with a link to the screen. A cashier sees the refusal's own message at the till.
- **Not built:** a license notice on the till before a shift is refused.

### Pointer, 2026-11-25: see ADR-019
ADR-019 records the direction for a native device agent, the defects to fix and the order of work before any install is enforced. It changes the direction of decision 4 (hardware binding) and of the rollout. Two of two PCs checked cannot supply all three hardware values.

## What this does and does not guarantee
- **Guarantees:** a copy of the images and volumes moved to another PC **without** the host helper's output fails the fingerprint check at activation and renewal. If a determined copier also copies `hardware.json` (it is unsigned and can be copied with the stack), only fork detection and certificate expiry limit the copy: two copies of one chain that both renew expose a fork, and the first to renew wins, but a fork is undetected if the original stops renewing. An unattended copy stops opening shifts within 30 to under 31 days. The provider holds evidence (a signed check-in log, fork records, the deployment watermark of stage-23 addendum 10, the audit trail) for a license dispute.
- **Does not guarantee:** it cannot stop a determined host administrator. TindaFlow is self-hosted, offline-capable PHP; any client-side check can be patched by someone who edits the code, rebuilds the image or mounts replacement files. The strength is Medium on purpose (D5): deter and detect. The 30-day life weakens the deterrent compared with the original 7 days: an unattended copy can trade for up to about 31 days, and a revocation or suspension reaches an offline client only after its certificate runs out. The enforceable protection remains the license agreement and copyright law. A copy started later with its clock set to the copy date still trades for the rest of its certificate plus one 18-hour shift, and can apply the same extension as the original.

## Consequences
- **Behaviour change.** A shop that stays offline past its certificate cannot open a new shift until it reconnects or the provider issues an extension. The provider must be reachable at least once in each certificate life, and the license agreement says so (support hours, a 4-business-hour target for extension requests, a continuity clause that delivers a perpetual offline license or an escrowed build with licensing disabled if the provider stops operating, and the stated revocation latency).
- **New operational duties.** Provider runbooks RB-1 to RB-9 (extension, clock rollback, hardware repair, fork, stale helper, lost break-glass password, chain re-chain after a restore, lost till browser, suspected personal data breach). Every backup restore needs a provider Re-chain (RB-7) until the self-service re-sync exists. The provider must keep the locally hosted control plane reachable (UPS, a second line, a hostname that survives IP changes, an offline key backup with a tested restore, a standby machine).
- **Data privacy.** The control plane holds no personal data of client staff or customers. Provider telemetry (IP address, client contact number, a sole proprietor's business details, fingerprint hashes) is the provider's own personal data under the Data Privacy Act (RA 10173). Hosting locally in the Philippines is expected to avoid a cross-border transfer; counsel confirms this and the provider's role. Remedies: a privacy notice and license agreement that name exactly the data collected, an access policy for any technician visit, proposed retention (logs 2 years, registry record contract term plus 5 years, for counsel to confirm), and a breach runbook (RB-9): where notification is required, the National Privacy Commission and affected people are told within 72 hours of knowledge (NPC Circular 16-03), and counsel decides. NPC registration is recorded as not required for the client or the provider, as relayed by the owner from data counsel and not independently verified; re-check if headcount reaches 250 or the NPC's other criteria apply (Circular 2022-04).
- **Code and data touched.** `license_state` is a new table, mutable by design (the heartbeat updates it); any certificate or extension history table is append-only and joins `database/scripts/harden_append_only_privileges.sql`, the `HardenDatabase` read-back and `AppendOnlyPrivilegesTest`. `Entitlement` and `TerminalSeats` read the certificate. `RoleCapabilityCatalog`, `UserService`, `UserController`, `UserFormPanel`, `CreditOverrideController` and `OverrideCodeService` change for the role rules. The `scheduler` service and an hourly `Schedule::command('tindaflow:license-renew')` are new.
- **Documents to amend as the work lands:** `error-catalog.md` (append `LICENSE_NOT_ACTIVE`; the `TERMINAL_LIMIT_REACHED` row's "expired" wording), `openapi.yaml` and `operation-inventory.md` (the `shiftOpen` 409, the license operations, `LICENSE_MANAGE`, the capability enum and tables), `api-design.md` (the capability list and the role table: MANAGER gains `USER_MANAGE`), `docs/02-domain/domain-model.md` §2.2 (the capability list), `stage-13-users.md` (a note on the historical "ADMIN only"), `offline-strategy.md` and the draft `deployment.md` (the new outbound renewal, the scheduler and the host helper), ADR-014 decision 6 and its consequence line, ADR-015, ADR-002, ADR-013 decision 5 and ADR-008 (each a pointer to this ADR), `docker/README.md` (steps 4 and 6 are replaced by `tindaflow:activate`), `docs/PROJECT-MANIFEST.md`, and the tests (`RoleCapabilityCatalogTest`, `UsersHttpTest`, `UsersAuditHttpTest`).
- **Residual risks, accepted.** A `USER_MANAGE` manager can create or impersonate approvers and lift approver lockouts. A host administrator can copy the machine key or edit `license_state`, and an offline copy is never detected if the original stops renewing. An activation code intercepted first gives the racer the business details. Whoever opens the sealed break-glass credential first can sign in until the owner changes the password. Forged certificates are possible until a compromised key is rotated, and offline clients learn of it only with their next image. Auto sign-in exposes the till account on the PC. Docker Desktop may drop support for Windows 10 22H2.

## Alternatives considered
- **Keep ADR-014 as is (a license never stops selling).** Rejected: it does not meet the requirement to bound copies.
- **Always-online validation of every sale.** Rejected: breaks D2; the canteen's internet is down for days.
- **Block sales at the moment of expiry.** Rejected: it can stop a canteen mid-service; replaced by shift-boundary enforcement.
- **A hardware dongle.** Rejected: cost and logistics per client, a lost dongle stops trading, and it is still bypassable by patching PHP.
- **TPM-backed attestation.** Not now: strongest binding, but complex on Windows with WSL2 and still bypassable by patching. Kept as later hardening.
- **PHP obfuscation or encoding (for example ionCube).** Rejected: licensing cost, harder debugging, Laravel compatibility risk; it only deters.
- **Short, phone-dictated extension codes.** Rejected: they need a shared secret on the client, which a copier extracts.
- **Ongoing master-data sync from the cloud.** Rejected: breaks D3 and puts personal data in the cloud.
- **A vendor admin account in each client.** Rejected by ADR-014: a standing credential into client data.
- **Rounding certificate life down to 05:00 (at most 30 days).** Rejected: a guaranteed maximum could cut a real outage to about 29 days; the round-up guarantees at least 30. D6 itself was raised from 7 to 30 days by the owner on 2026-11-24 (the closest POS peer found allows 14 days); the pilot logs each client's longest offline gap.
- **Removing the admin screens from the client build.** Not adopted: hiding screens is a product decision, not a security control, and Terminals and Store setup need `/admin`. Lazy-loading the ADMIN-only routes is an optional size optimization.
- **Docker Engine inside WSL2 started by a SYSTEM task.** Not adopted: it avoids auto sign-in but is not a supported Docker Desktop setup.
- **A cloud-hosted control plane with a cloud KMS.** Not chosen: the control plane carries license data only, so the provider hosts it locally and keeps the signing key in its own hardware module.

## Rollout and what still has to be proven
Seven phases, each with its own tests; enforcement is switched on only after the pilot proves it never blocks a valid shift: (1) a spike, (2) roles, Manager area, local import and the activation CLI with the certificate verifier, (3) the control plane MVP, (4) the entitlement state machine, trusted time, `EnsureLicenseActive`, the scheduler and the banner, (5) offline extension, revocation, alerts and runbooks, (6) image-only distribution, ADRs and docs, (7) the TSC activation rehearsal, then a 14-day pilot, in report-only for its first 7 days and then enforcing.

Not design gaps, but still to do:
- **Phase 1 spike:** Docker Desktop starts unattended after a power cut; the monotonic clock source behaves under Docker Desktop and WSL2; the bind mount of `C:/ProgramData` shows a renamed file; the provider's public address is not behind carrier-grade NAT.
- **Counsel** reviews the license agreement text and the proposed retention periods before signature.
- **Client commissioning checks** before the Phase 7 rehearsal: the printer model (a 58 mm slip printer, ADR-016, installed as an OS printer, ADR-007) and the Windows 10 ESU purchase. The client supplied the slip footer text, Windows 10 Pro build 19045 and the drive type on 2026-11-24: the drive is a hard disk, which ADR-013 decision 2 lists as unsupported, so the owner accepted a written exception for the pilot (recorded in ADR-013). The pilot measures sale and shift-close time on that PC, hourly dumps to a second disk stay mandatory, and the disk is replaced with an SSD if checkout is slow or the disk shows any fault.
